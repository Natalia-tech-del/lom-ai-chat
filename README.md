# LOM AI — веб-клиент образовательного ИИ-агента

Небольшой веб-клиент, в котором школьник может вести несколько диалогов с ИИ-агентом, получать ответы с имитацией потоковой генерации и наблюдать за основными этапами выполнения запроса.

Настоящая языковая модель не подключена: поведение агента имитируется локальным mock-agent.

Короткая запись экрана: [посмотреть видео](https://drive.google.com/file/d/1IcsoRFs0UaIngAGJqDCzEp3OaQq0cWa5/view?usp=sharing).

## Возможности

- Отправка сообщений и продолжение диалога с учётом предыдущей истории.
- Создание нескольких диалогов и переключение между ними с сохранением истории.
- Постепенное отображение ответа агента (streaming).
- Отображение этапов работы агента: обработка запроса, использование инструмента, формирование ответа, завершение и ошибка.
- Mock-калькулятор (например, для запроса «Сколько будет 17 × 24?»).
- Демонстрация ошибки по фразе «покажи ошибку» и возможность повторить запрос.
- Остановка генерации.
- Сохранение диалогов в `localStorage`.
- Пустое состояние и отображение длинных сообщений.

## Запуск

Требуется Node.js 20+ и npm.

```bash
npm ci
npm run dev
```

Откройте адрес, указанный в терминале (обычно http://localhost:5173).

Дополнительные команды:

```bash
npm run build
npm run lint
npm test
```

Диалоги сохраняются в `localStorage` под ключом `lom-ai-conversations`.

## Архитектура

Структура проекта организована по принципам Feature-Sliced Design (FSD). Зависимости между слоями направлены сверху вниз: слой может импортировать модули из нижележащих слоёв.

Основные части приложения:

- `src/app` — точка входа, тема Mantine, ErrorBoundary.
- `src/pages/chat` — страница чата.
- `src/widgets/conversation-list` — список диалогов и создание нового чата.
- `src/widgets/chat-thread` — лента сообщений, примеры запросов и автопрокрутка.
- `src/features/send-message` — отправка сообщений, запуск, остановка и повторное выполнение запроса.
- `src/entities/conversation` — типы диалогов и сообщений, Zustand-store.
- `src/shared/mock-agent` — сценарии mock-agent и генератор событий.

### Управление состоянием

Состояние диалогов хранится в одном Zustand-store.

Основные данные:

- `conversations` — список диалогов с историей сообщений;
- `activeConversationId` — идентификатор открытого диалога.

У каждого диалога свои сообщения и состояние текущего выполнения (`activeRun`), которое равно `null`, если запрос не выполняется.

Каждое сообщение содержит текст, роль, время создания и статус (`pending`, `streaming`, `done`, `error`, `stopped`).

UI-компоненты подписываются на необходимые части store и отображают актуальное состояние. Логика отправки сообщений и взаимодействия с агентом вынесена в `features/send-message`.

Для сохранения данных между перезагрузками используется Zustand persist с `localStorage`.

`activeRun` не сохраняется. При восстановлении состояния сообщения, находившиеся в статусах `pending` или `streaming`, переводятся в `stopped`, поскольку после перезагрузки выполнение агента не может продолжиться. Такой запрос можно запустить повторно.

`AbortController` хранится в `Map` вне store, чтобы не помещать объект управления асинхронным выполнением в сериализуемое состояние приложения.

### Mock-agent и streaming

Mock-agent работает локально и не обращается к внешнему AI API.

Он принимает историю текущего диалога и `AbortSignal`, после чего отдаёт последовательность событий через асинхронный генератор (`AsyncGenerator`).

Используются следующие типы событий:

- `status` — высокоуровневый статус для пользователя, например «Анализирую задачу», «Использую калькулятор», «Формирую ответ»;
- `tool_call` — имитация вызова инструмента;
- `tool_result` — результат работы инструмента;
- `text_delta` — очередной фрагмент текста ответа;
- `completed` — успешное завершение;
- `error` — ошибка выполнения.

Технические события вызова инструмента не отображаются пользователю как внутренняя цепочка рассуждений. Вместо этого интерфейс показывает понятные статусы работы агента.

Фрагменты ответа поступают с искусственной задержкой и последовательно добавляются в сообщение ассистента.

Предусмотрено несколько сценариев: объяснение второго закона Ньютона и закона Ома, упрощение предыдущего объяснения с учётом истории диалога, использование калькулятора, подсказка без готового ответа, ошибка и ответ по умолчанию.

### Управление выполнением запроса

Функции `startRun`, `stopRun` и `retryRun` находятся в `features/send-message`.

Для каждого диалога используется отдельный `AbortController`. Это позволяет остановить выполнение запроса и независимо управлять генерацией в разных чатах.

При обработке событий контроллер проверяет, является ли текущий запуск актуальным. События от предыдущего запуска игнорируются, чтобы они не могли изменить состояние после остановки или повторного запуска.

Повторное выполнение доступно для последнего сообщения ассистента со статусом `error` или `stopped`. Перед повтором текст сообщения сбрасывается с помощью `resetAssistantMessage`, после чего запускается новый запрос. Сообщение пользователя при этом не дублируется.

Пока агент генерирует ответ, в активном диалоге вместо отправки доступна остановка генерации. При переключении на другой диалог его история и состояние сохраняются, а уже запущенная генерация продолжается в фоне.

## Архитектурные решения

- Mock-agent не зависит от React и Zustand, а store не зависит от реализации агента. Связующим звеном выступает feature отправки сообщения.
- Событийная модель mock-agent позволяет в дальнейшем заменить локальную реализацию на взаимодействие с настоящим AI API.
- Состояние выполнения хранится отдельно для каждого диалога.
- Для отмены асинхронного выполнения используется `AbortController`.
- В историю, передаваемую агенту, включаются сообщения пользователя и только завершённые ответы ассистента. Незавершённые ответы не попадают в контекст следующего запроса.

## Известные ограничения

- Агент использует заранее заданные сценарии и простые условия, а не настоящую языковую модель.
- Сценарий ошибки привязан к тексту запроса. Повтор запроса «покажи ошибку» снова приводит к ошибке.
- Нет возможности удалять и переименовывать диалоги.
- Данные хранятся только в `localStorage` и не синхронизируются между устройствами.
- После перезагрузки страницы незавершённый запрос не продолжается.

## Что можно улучшить

- Подключить настоящий AI API, сохранив текущую событийную модель взаимодействия.
- Добавить удаление и переименование диалогов.
- Улучшить отображение прерванной генерации, например добавить явную подпись «Ответ прерван».

## Использование AI-инструментов

В процессе разработки использовался Cursor как вспомогательный инструмент. Он помогал создавать черновики отдельных модулей и компонентов, использовался для подготовки документации.

AI-инструмент использовался как помощник при разработке, но предложенные решения не принимались автоматически: их приходилось разбирать, проверять на соответствие остальному коду и адаптировать под выбранную архитектуру.

Примеры решений, которые были пересмотрены:

1. Повторный запуск после ошибки. Первоначальный вариант предлагал использовать `appendAssistantText` с пустой строкой для сброса сообщения. Вместо этого была добавлена отдельная операция `resetAssistantMessage`, а логика повторного запуска вынесена в `retryRun`. Так назначение каждой операции стало более явным.
2. Восстановление состояния после перезагрузки. Первоначальная реализация через `onRehydrateStorage` и `setState` ненадёжно восстанавливала статусы незавершённых сообщений. После проверки поведения этот вариант был заменён на обработку восстановленного состояния через `merge` в конфигурации persist.
